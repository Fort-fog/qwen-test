# BOLTUN E2E envelope contract — `boltun-e2e-v1`

Normative description of the end-to-end encryption format as **actually
implemented** in `server/internal/e2e/e2e.go` (Go) and consumed by
`server/internal/client/e2e_handler.go`. The Dart client port MUST match
this document byte-for-byte. Any change to the Go implementation requires a
version bump (`v: 2`, new scheme string), never a silent edit.

The relay is zero-knowledge: it only ever sees opaque base64 strings inside
JSON payloads. It must never parse, store keys beyond announced public keys,
or attempt decryption.

## 1. Algorithms & sizes

| Purpose            | Algorithm                                   | Size |
|--------------------|---------------------------------------------|------|
| Identity key pair  | X25519 (RFC 7748)                           | 32B private / 32B public (little-endian u-coordinates) |
| Per-message ephemeral key | X25519, freshly generated per Seal   | same |
| KDF                | HKDF-SHA256 (RFC 5869), output L = 32        | AES-256 key |
| AEAD               | AES-256-GCM                                 | nonce 12B, tag 16B (appended to ciphertext by GCM) |

Standard X25519 clamping applies on private keys (handled by the primitive).

## 2. Key roles

- Each device owns a **long-lived identity key pair** (private key never
  leaves the device; public part announced at HELLO, see §6).
- Every encrypted message uses a **fresh ephemeral X25519 key pair**; its
  public key travels in the envelope header. This gives per-message forward
  secrecy against a later identity-key compromise of the *ephemeral* side.

## 3. Shared secret

```
shared = X25519(eph_priv, recipient_pub)      # Seal side
shared = X25519(recip_priv, env.eph_pub)      # Open side — identical value
```

Raw 32-byte X25519 output, no hashing before HKDF.

## 4. Key derivation (HKDF)

```
salt = eph_pub                       # 32 raw bytes from envelope header
info = "boltun-e2e-v1|" + hex(sender_pub) + "|" + hex(recipient_pub) + "|" + msg_id
key  = HKDF-SHA256(ikm=shared, salt=salt, info=info, L=32)
```

- `hex(...)` is **lowercase hex of the raw 32-byte public key** (64 chars).
- Roles inside `info` are fixed: sender first, recipient second — both peers
  can reconstruct it, so derivation is symmetric.
- `msg_id` is the transport packet's `msg_id` string (16 random bytes
  lowercase hex, generated by the sender *before* sealing).

## 5. Envelope wire format

Raw envelope bytes (inside `env` after base64):

```
offset 0      : 1 byte   version = 0x00
offset 1..32  : 32 bytes ephemeral public key (raw, little-endian)
offset 33..44 : 12 bytes AES-GCM nonce (CSPRNG per message)
offset 45..   : ciphertext || 16-byte GCM authentication tag
```

Minimum valid length: `1 + 32 + 12 + 16 = 61` bytes.

### AAD (GCM additional authenticated data)

```
aad = "boltun-aad-v1|" + hex(sender_pub) + "|" + hex(recipient_pub) + "|" + msg_id
```

binds the ciphertext to the claimed sender identity, the recipient identity
and the message id — stripping, re-routing and replay-under-another-msg-id
all fail the tag check.

## 6. Transport JSON layer

MESSAGE payload object (`{"kind":"e2ee","v":1,"env":"..."}`):

```json
{
  "kind": "e2ee",
  "v": 1,
  "env": "<base64 STD (with padding) of the raw envelope bytes>"
}
```

Base64 alphabet: standard RFC 4648 (`+/`), **not** URL-safe.

Public-key announcement / lookup (see docs/PROTOCOL.md for framing):

- `HELLO.payload.identity_pub` — base64 std of this device's 32-byte
  identity public key (optional; server rejects values that don't decode to
  exactly 32 bytes).
- `KEY_REQUEST.payload`: `{"target_device_id": "<device>"}`
- `KEY_RESPONSE.payload`: `{"target_device_id": "...", "found": true|false,
  "identity_pub": "<base64 std>"}` — `identity_pub` present only when found.

## 7. Seal / Open behaviour on errors

Seal (sender):
- entropy failure → error, nothing sent.

Open (recipient), in order:
1. `len(env) < 61` → `ErrShortEnvelope` ("envelope too short")
2. `env[0] != 0` → `ErrBadVersion` ("unsupported envelope version")
3. base64 decode failure at the JSON layer → client reports
   `E2E_MALFORMED_ENVELOPE`
4. GCM tag mismatch (tampered ciphertext/tag, wrong recipient key, wrong
   sender binding, wrong msg_id) → `ErrOpenAuthFailed`
   ("authentication tag check failed"). **All failures are indistinguishable
   on the wire** — the relay cannot tell why an envelope didn't open.
5. Sender identity key not yet known → message is queued (deferred queue,
   max 100/peer) and retried automatically when KEY_RESPONSE arrives; UI
   shows `E2E_NO_SENDER_KEY` meanwhile.

No plaintext is ever delivered for a failed Open; failures surface as
explicit errors, never silently dropped.

## 8. Mandatory checks for implementers (Dart port)

- reject envelopes shorter than 61 bytes or with version ≠ 0x00;
- use lowercase hex for pubkeys in `info`/`aad`;
- generate the ephemeral key pair and the 12B nonce from a CSPRNG per
  message; NEVER reuse a (key, nonce) pair;
- bind `msg_id` before sealing (generate msg_id first);
- base64-std encode/decode `env`;
- compare UTF-8 plaintext after decrypt; treat any GCM failure as fatal for
  that message.

## 9. Trust limitations (MUST be respected by clients)

A key received via KEY_RESPONSE is merely **announced** by the peer at its
HELLO and forwarded verbatim by the relay. Ownership is **not proven** —
this exchange is NOT resistant to a malicious/MITM relay. Out-of-band
fingerprint verification (e.g. SHA-256 of the identity pubkey shown as
short code) is planned future work. Clients must not present E2E as
authenticated until then.

## 10. Cross-language test vectors

File: `server/testdata/e2e_vectors.json` (generated by
`go test ./internal/e2e/ -run TestGenerateCrossLanguageVectors`).

Contains a deterministic vector: fixed **test-only** identity/ephemeral
private keys, `msg_id`, nonce, plaintext, expected derived key hex, expected
full envelope hex/base64. These secrets are fixtures for interoperability
testing only — they must never be used in production or treated as real
credentials.

The vector was independently verified against OpenSSL-backed primitives
(Python `cryptography`: X25519 + hand-rolled HKDF-SHA256 + AESGCM) — key and
plaintext reproduced exactly. The Dart port must pass the same checks:

1. derive `sender_pub`/`recipient_pub`/`ephemeral_pub` from the given
   private hexes → equal to published pub hexes;
2. compute shared secret + HKDF per §3–§4 → equal to `derived_key_hex`;
3. rebuild the envelope per §5 with the fixed nonce → equal to
   `envelope_hex`;
4. Open `envelope_b64` → `plaintext_utf8`; tamper any byte → auth failure.
